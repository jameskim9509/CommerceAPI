# ADR 008: 주문 정합성 통합 시나리오 — 원하는 장애와 주변 장애의 동시 검증

- 상태: 제안 (Proposed)
- 작성일: 2026-07-06
- 관련 코드: [orderApi SAGA](../orderApi/src/main/java/com/zerobase/orderApi/saga/) · [userApi SAGA](../userApi/src/main/java/com/zerobase/userApi/saga/) · [qa/02-consistency/](../qa/02-consistency/)
- 관련 ADR: [ADR-001](./001-idempotency-double-payment-prevention.md) · [ADR-002](./002-optimistic-lock-stock-concurrency.md) · [ADR-003](./003-choreography-saga-compensation.md) · [ADR-004](./004-transactional-outbox-pattern.md)

## 컨텍스트

ADR-001 ~ 004 는 각 정합성 메커니즘을 **개별적으로** 정당화했다.

| ADR     | 메커니즘                                  | 격리 검증                  |
| ------- | ----------------------------------------- | -------------------------- |
| ADR-001 | HTTP 멱등성 (`Idempotency-Key` + Redis) | 더블클릭 / 타임아웃 재시도 |
| ADR-002 | 재고 낙관적 락 (`ProductItem.@Version`) | 동시 주문 Lost Update      |
| ADR-003 | Choreography SAGA + 보상                  | 결제/재고 분산 트랜잭션    |
| ADR-004 | Transactional Outbox (`outbox_events`)  | dual-write 문제            |

문제는 **실제 트래픽에서는 이 네 메커니즘이 한 부하 안에서 동시에 발화**한다는 것이다. 개별 시나리오가 각각 통과해도, 이들이 서로 충돌 없이 합성되어 **최종 DB 상태가 정합**한지는 별도로 증명해야 한다. 예를 들어 낙관적 락 충돌(ADR-002이 SAGA 보상(ADR-003)을 유발하고, 그 보상 이벤트가 아웃박스(ADR-004)를 통해 발행되며, 그동안 같은 사용자가 멱등 재전송(ADR-001)을 하는 상황이 한 요청 안에서 겹칠 수 있다.

또한 본 프로젝트의 도메인 모델은 결제·환불을 **잔액 원장**(`customer_balance_history`)으로, 재고를 **`product_item.count` 단일 컬럼**으로 표현한다. 따라서 정합성 시나리오와 그 검증도 이 **모델 위에서** 정의한다.

본 ADR 의 목적은 두 가지다.

1. 위 네 메커니즘이 동시에 발화하는 **주문 10만 건 규모의 통합 정합성 시나리오를 새로 설계**하고, 그 최종 정합성을 교차 DB 불변식으로 판정하는 방법을 정의한다.
2. 현재 구현이 **아직 다루지 못하는 것을 후속 과제로 남긴다**.

### "원하는 장애" 와 "주변 장애"

이 통합 시나리오는 *원하는 장애와 주변 장애*를 검증한다. 그 둘을 다음과 같이 정의한다.

| 구분                                          | 정의                                                                                                                   | 본 프로젝트에서의 구체 조건                                                                                                                                                                                                      |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **원하는 장애** (대비한 장애 상황)      | 정합성을 깨뜨릴 수 있어**전용 방어 메커니즘을 구현**했고, 이 시나리오가 발화·검증하는 실패                      | ① 중복 주문/결제, ② 재고 충돌(초과판매), ③ 결제 후 재고 실패→환불, ④ 잔액 부족→결제 실패, ⑤ 잔액 동시성 Lost Update, ⑥ 이벤트 중복/역순 배달                                                                             |
| **주변 장애** (대비하지 못한 장애 상황) | 아직**대비하지 못해** 데이터 정합성을 깰 수 있는 예측 불가 비정상동작(인프라 다운·크래시·인프라 자체 한계 등) | 인프라 다운·네트워크 timeout·메시지 유실·부분 크래시 중**정합성을 깰 수 있는 것** — 지금 코드에서 재현되는 실재 결함 **T1–T4** (상세 [§ 주변 장애](#주변-장애)). 정합성 무관·대상 부재 항목은 제외 |

## 결정

**주문 10만 건 규모의 단일 통합 부하**에서 원하는 장애 6종을 동시에 발화시킨 뒤, 다음 3단계로 최종 정합성만 판정한다.

1. **부하 종료** — k6 가 요청 전송을 멈춘다.
2. **정착 대기** — 이 시스템은 최종 일관성(eventually consistent)이라, 부하 직후에도 보상 이벤트(환불·주문 상태)와 아웃박스 발행이 Kafka 를 타고 **아직 흐르는 중**이다. 이 비동기 흐름이 멎을 때까지 기다린다.
3. **교차 DB 불변식** — 그 뒤 `orders` DB 와 `user` DB 를 함께 조회해, **정착 후 최종 DB 상태**로 불변식을 판정한다.

### 통합 시나리오 구성 (기본 10만 건 주문)

```text
"작은 고객 풀이 반복 주문해 만드는 10만 건의 주문에, 한정 재고 hot SKU 경합·
 잔액 부족·멱등 재전송을 섞어 원하는 장애 6종을 한 부하에서 동시에 발화시킨다."
```

**트래픽 구성**:

| 주문 유형           | 비율 | 10만 기준 |
| ------------------- | ---: | --------: |
| 일반 정상 주문      |  85% |    85,000 |
| 한정 재고 SKU 경합  |   8% |     8,000 |
| 고객 잔액 부족      |   5% |     5,000 |
| 멱등 재전송 overlay |   2% |     2,000 |
| 합계                | 100% |   100,000 |

### 주입 조건 (발화 벡터)

원하는 장애 6종은 **모두 시나리오가 의도적으로 발화**시킨다 — 우연이 아니다. 다만 현재 구현의 주입 지점은 **시드 데이터·토폴로지·부하 설정** 이다. **주입 조건 자체는 원하는 장애를 강제하는 발화 환경**이다. 아래 표에 각 주입 조건의 인스턴스·재고·고객 풀과 발화하는 원하는 장애를 작성했다.

| 주입 조건 (발화 벡터) | 무엇으로 / 구체값                                                                                                                                                                                              | 발화하는 원하는 장애                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 동시성                | 토폴로지: orderApi ≥4 인스턴스 × Kafka ≥4 파티션 (같은 hot SKU/고객 병렬 처리)                                                                                                                              | ② 재고 락 경합 · ⑤ 잔액 락 경합 · ⑥ 이벤트 중복/역순  |
| 재고 소진 압력        | 시드: hot SKU 재고(예`count=1,000`) ≪ 경합 수요(8,000)                                                                                                                                                      | ② 초과판매 · ③ 재고 소진→환불                          |
| 같은 고객 경합        | 시드: 주문 수보다 훨씬 작은 고객 풀(예 5,000~10,000명,`P ≪ 10만`), 결제가능 다수 + 잔액부족 소수. **고객마다 `customer_balance_history` 기준 행 시드 필수** | ⑤ 잔액 락 경합 · ④ 결제 실패 분기                       |
| 부하 설정             | k6: 재전송율(멱등) · 잔액부족율(broke)                                                                                                                                                                        | ① 중복 결제 · ④ 잔액 부족                               |
| 아웃박스 타이밍       | 구조:`OutboxPoller` 비동기(1초) + 종료 후 정착 대기                                                                                                                                                          | (발행 backlog 가 정착 후`sent_at IS NULL = 0` 으로 해소) |

> 정합성을 깨는 주변 장애는 [§ 주변 장애](#주변-장애)에서 주입한다 — 대부분(T1–T4)은 **인프라 카오스로 지금 주입 가능**하다.

### 주변 장애

주변 장애는 **정상 경로 주위의 예측 불가 비정상동작 중 데이터 정합성을 깰 수 있는 것**만 다룬다 (인프라 다운·네트워크 timeout·메시지 유실·부분 크래시류 + 인프라 자체 durability 한계). 정합성 불변식과 무관한 것(UX·API 계약 등)은 다루지 않는다. 아래 T1–T4 은 별도 폴트 인젝션 훅이나 net-new 컴포넌트 없이 **현재 코드에서 순수 인프라 카오스로 주입해 재현되는 실재 정합성 결함**이다. **이 장애들도 시나리오에서 주입한다**(각 행의 `주입 방법(현재)` 열) — 다만 원하는 6종과 달리 아직 방어가 없어 **넣으면 깨진다**. 즉 주변 장애 주입의 목적은 "통과 확인"이 아니라 **깨지는 지점(복원력 gap) 노출**이다 (측정 시 bounded 고정 카오스 스케줄로 통합 런에 주입 → 잔여 r; 근본 수정은 본 ADR 범위 밖).

#### 현재 코드에서 재현되는 정합성 결함

### 원하는 장애에 대한 발화·검증 매핑

각 장애 → 어떻게 발화(주입)되는가 → 무엇으로 관측·검증하는가. (주입 벡터 상세는 [§ 주입 조건](#주입-조건-발화-벡터).)

| #  | 원하는 장애               | 발화 메커니즘 (실제 코드)                                                               | 관측 불변식 (교차 DB)                                                                               |
| -- | ------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| ① | 중복 주문/중복 결제       | 같은`Idempotency-Key` 재전송 → Redis `idem:order:{key}`중복 (ADR-001)              | k6`duplicate_order_responses = 0` (같은 키 → 같은 `orderId`)                                   |
| ② | 재고 초과판매             | 파티션 병렬 재고 차감 →`ProductItem.@Version` 충돌 (ADR-002)                         | `product_item.count ≥ 0`, `(초기재고 − count) = Σ CONFIRMED 수량`, `CONFIRMED ≤ 초기재고` |
| ③ | 결제 후 재고 실패 → 환불 | 재고 소진/락 충돌 →`StockReservationFailed` → 환불 → `PaymentReverted` (ADR-003) | 돈 보존:`Σ 잔액감소 = Σ total_price(CONFIRMED)`, `PENDING/PAID 잔여 = 0`                      |
| ④ | 잔액 부족 → 결제 실패    | broke 고객 →`NOT_ENOUGH_BALANCE` → `PaymentFailed` (ADR-003)                      | `orders.status=FAILED` + `failure_reason='결제 실패: 잔액이 부족합니다.'`, 음수 잔액 = 0        |
| ⑤ | 잔액 동시성 Lost Update   | 같은 고객 동시 결제/환불 →`Customer.@Version` → 30회 재시도 (PR #63)                | 음수 잔액 = 0, 돈 보존 성립(재시도로 유실 없이 수렴)                                                |
| ⑥ | 이벤트 중복/역순 배달     | Kafka at-least-once + 파티션 →`processed_events(event_id, consumer_name)` (ADR-003)  | 중복 결제/환불 없음(돈 보존), 재고 이중 차감 없음                                                   |

> **핵심:** 원하는 장애 6종은 모두 의도적으로 주입되며, 통합 시나리오의 가치는 이렇게 **여러 장애를 동시에 주입한** 상태에서도 네 메커니즘(멱등성·낙관적 락·SAGA 보상·아웃박스)이 서로 충돌 없이 정합성을 유지함을 증명하는 데 있다.

### 검증 — 교차 DB 불변식 (판정 방법)

원하는 장애 ②③④가 모두 SAGA 상태 머신 위에서 갈라진다. `Order` 상태는 **정확히 4개** (`PENDING → PAID → CONFIRMED / FAILED`) 이며, 모든 실패는 `FAILED` 로 수렴하고 `failure_reason` 자유 텍스트로만 구분된다. (forward·두 보상 경로의 전체 시퀀스는 [ADR-003](./003-choreography-saga-compensation.md).)

- **결제 후 재고 실패(③)** 는 ③ 자체를 따로 토글하는 게 아니라, **재고 소진(②)을 주입한 결과 필연적으로 뒤따르는 후속 실패**다. 재고 ≪ 수요 조건을 주입하면, 소진 후 주문은 결제(잔액 차감)까지 성공한 뒤 재고 차감에서 실패 → 환불 보상 → `FAILED` 로 수렴한다.
- **모든 실패가 `FAILED` 로 붕괴**하므로, orders 테이블만으로는 "낙관적 락 충돌"과 "재고 소진(NOT_ENOUGH_ITEM_COUNT)"을 구분할 수 없다. 둘 다 `failure_reason='재고 차감 실패 후 환불 완료'` 로 기록된다. 구분되는 사유는 **전이적인** `StockReservationFailed` 이벤트 페이로드(`재고 동시성 충돌` vs 재고 부족)와 userApi `customer_balance_history.description` 에만 남는다.

정착 대기 후, `orders` DB 와 `user` DB 를 조회해 3대 불변식·9개 체크를 판정한다. **재고 델타와 돈 보존**으로 검증한다. 런 스코프는 **시드 명명 규칙**(고객 username/email 접두사, hot SKU id)으로 잡는다.

**① 멱등성 위반 = 0** (원하는 ①)

```
duplicate_order_responses == 0     # k6 가 같은 키 재전송 시 orderId 동일함을 확인
```

**② 초과판매 = 0** (원하는 ②) — `product_item.count` 델타로 검증 (`초기재고` = 시드 상수)

```sql
-- 재고 음수 없음
SELECT COUNT(*) FROM product_item WHERE count < 0;                    -- = 0
-- 차감량 == CONFIRMED 주문 수량
SELECT (초기재고 - (SELECT count FROM product_item WHERE id = :hot))  -- 소비량
     = COALESCE(SUM(oi.count), 0)                                     -- CONFIRMED 수량
  FROM order_items oi JOIN orders o ON oi.order_id = o.id
 WHERE o.status = 'CONFIRMED' AND oi.product_item_id = :hot;
-- CONFIRMED 수량 <= 초기재고
```

**③ 결제·재고 정합성 = 0** (원하는 ③④⑤) — 돈 보존으로 검증

```sql
-- 중간 상태 잔여 없음 (정착 후에도 PENDING/PAID 면 SAGA 미종결)
SELECT COUNT(*) FROM orders WHERE status IN ('PENDING','PAID') AND <scope>;   -- = 0
-- 아웃박스 미발행 없음 (양 DB)
SELECT COUNT(*) FROM outbox_events WHERE sent_at IS NULL;                     -- = 0 (orders, user)
-- 돈 보존: 잔액 감소 총액 == CONFIRMED 결제 총액
--   (환불된 주문은 차감 후 환불되어 순변화 0 → 오직 CONFIRMED 만 순차감)
SELECT (초기잔액합 - 현재잔액합) = SUM(total_price) FROM orders WHERE status='CONFIRMED';
-- 음수 잔액 없음
SELECT COUNT(*) FROM customer WHERE balance < 0 AND <scope>;                  -- = 0
```

### 측정 계획 / KPI — 무방어 vs 방어 집계 before/after

검증은 위 §검증의 3대 불변식·9개 체크로 판정한다. 실측치는 이 시나리오 하네스를 구현·실행한 뒤 채운다(표기는 전부 `⟨측정전⟩`).

#### 측정 형태 — 6개 방어를 "다 끈 무방어" vs "다 켠 현재", 같은 부하·같은 카오스

방어 효과를 하나의 집계 KPI로 보이려면, **6개 방어(①~⑥)를 전부 끈 무방어 빌드(control)**와 **전부 켠 현재(treatment)**를 같은 부하·같은 층1 트리거·**같은 고정 카오스 스케줄** 아래 돌려 **교차 DB 불변식 위반 총수**를 비교한다.

- **control (무방어)** → desired 위반 대량 + 카오스 잔여 ≈ **N**
- **treatment (현재)** → desired 방어(→0) + 카오스 잔여 ≈ **r** (0 아님)
- **KPI = N → r** — "6개 정합성 방어 설계로 통합 부하에서 정합성 위반 N → 소수 r 감소". r이 0 아닌 건 카오스(6개 방어 대상이 아닌 주변 장애 T1–T4)가 **양쪽에 똑같이** 남기 때문(감소분 = 방어가 실제로 커버한 부분).

#### 이건 "개별 귀속 없는 집계 주장"이다 (한계)

6개 방어를 한꺼번에 토글하므로:

- **개별 귀속 불가** — "`@Version`이 초과판매를 막았다"는 못 하고 "6개 방어 설계가 위반을 N→r 줄였다"만 주장.
- **N은 증폭됨** — ① 없으면 중복주문 → ②⑤ 경합 폭증. 근본원인 하나가 하류 위반 여럿을 낳아 N이 부풀어(현실적이나 시스템 고유값 아님).
- **①(멱등)은 9개 SQL 불변식에 안 잡힘** — 중복 주문은 돈 보존을 안 깨(두 주문이 각자 정당 결제). k6 `duplicate_order_responses`를 집계에 함께 포함해야 ①이 반영됨.
- (단일 변수 clean delta가 필요하면 **⑤ 잔액 락**만 예외 — `f0a48d5~1` vs `f0a48d5` git 짝 실험이 공짜·단일변수라 집계 옆 보조 증거로 붙일 수 있음.)

#### control(무방어) 빌드

**과거 커밋 체크아웃이 아니다** — 초기 커밋엔 SAGA·아웃박스·주문 흐름 자체가 없어 "6개 방어만 없고 나머진 그대로"인 clean 지점이 없다. 대신 **현재 코드(treatment)에서 6개 방어만 떼낸 전용 브랜치 `control/no-defense`(tag `v1`)** 를 만든다: ① 멱등 게이트 off · ②/⑤ `@Version` 제거 · ⑥ `processed_events` dedup 제거 · ③④ 보상 게이트 off. 운영 코드(treatment)엔 방어-off 스위치를 두지 않아(footgun 방지) 무방어 소스는 이 브랜치에만 존재한다. **측정은 브랜치=arm** — `v1` 을 체크아웃해 같은 QA 하네스를 돌리면 control(무방어), 방어 브랜치(feature/main)에서 돌리면 treatment 다(별도 control 이미지·오버레이·토글 없음; 상세 [qa/02-consistency/README.md](../qa/02-consistency/README.md)). 변형 버그가 위반으로 오계수되지 않게, **무카오스·무트리거 clean 부하로 pre-flight 스모크** 후 사용.

#### 재현 하네스 요구사항

잔여는 blast-radius라 하네스가 처리량·정착·카오스 타이밍을 통제해야 한다. 새 하네스는 반드시:

1. **처리량 고정** — `constant-arrival-rate`(고정 RPS + pre-alloc VU) + 주입 전 워밍업 (가변 `ramping-vus` 금지).
2. **카오스를 부하 진행도에 앵커** — "CONFIRMED K건 도달 시 폴트, 지속 고정". 스케줄을 `(진행도-앵커, 폴트, 지속)` 삼중항으로 공표. **bounded**(T1–T4를 각기 다른 진행도 지점에). control·treatment 양쪽 바이트 동일 적용.
3. **정착은 고정 sleep 아니라 quiescence 게이트** — 양 DB `sent_at IS NULL = 0` AND `PENDING/PAID = 0` AND consumer lag = 0 이 K회 연속.
4. **N회(≥10) interleaved 반복** — 잔여는 점추정 금지, 전 run 원값·중앙값·범위 공표. control이 cascade로 대부분 PENDING 붕괴한 run은 **VOID**(baseline 부적격).

### 후속 과제 (Future Work)

본 ADR 범위 밖. 별도 `docs:`/작업으로 분리한다.

- **ADR-004 상태 정정** — 아웃박스는 양 모듈에 **완전히 구현**됐으나 헤더가 아직 `제안(Proposed)`. `수용(Accepted)` 으로 갱신 필요.
- **DLQ + 수동 정산 큐 (미착수 · 향후 과제)** — 자동 복구가 끝내 실패한 건을 격리·추적할 저장소. 현재 Kafka 컨슈머는 에러 핸들러 설정이 없어 **스프링 부트 기본 `DefaultErrorHandler`(약 10회 in-memory 재시도 후 log-and-commit = 메시지 드롭)** 로 동작하고, 잔액 낙관적 락은 30회 재시도 후 rethrow 할 뿐 — 격리 저장소가 없다("무한 재배달"이 아니라 **유한 재시도 후 조용한 유실**). "운영 격리"를 실제로 관측하려면 net-new 컴포넌트가 필요.
- **아웃박스 poison-row HOL 격리 (미착수)** — `OutboxPoller` 가 첫 실패 시 `break`(순서 보존)라 발행 불가 row 1건이 그 모듈의 이후 모든 outbox 를 무기한 차단(HOL block). 재시도 상한 후 **개별 skip/격리**로 수정.
- **per-fault 귀속 (관심사 아님)** — 어떤 폴트(T1/T2/…)가 어떤 위반을 냈는지 per-request 로 쪼개려면 `test_run_id`(+`fault_type`) 컬럼과 폴트 인젝션 훅(`X-Extra-Fault-*`)이 필요하다. 본 KPI 는 잔여를 **총량으로만** 보므로 구축하지 않는다(주변 장애 대부분 T1–T4 은 인프라 카오스로 이미 주입 가능하며, 필요해지면 선행 과제로 분리).
- **낙관적 락 서술 정합** — ADR-002 의 "409 STOCK_CONFLICT, 클라이언트 재시도"는 **동기** 서술이다. 실제 SAGA 런타임에서는 `StockConsumer` 가 예외를 잡아 `StockReservationFailed` 보상으로 변환하며(클라이언트는 이미 200/PENDING 수신), 낙관적 락 정확성은 **결과**(음수재고 0, 차감==CONFIRMED, version==차감횟수, 실패건 환불)로 검증한다. ADR-002 에 이 런타임 차이를 보강.
