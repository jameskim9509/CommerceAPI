# ADR-005 시나리오 3 측정 결과 — orderApi 부하 분산

- 측정 일자: 2026-08-06 (1 · 2 · 4 대 **동일 바이너리**)
- 측정 대상 빌드: `92d23d1` 워킹트리에서 빌드한 jar
- 측정 환경: Docker Desktop 29.5.2 단일 노드, 16 CPU / 15.2 GiB
- 자원 한도: orderApi·userApi 2 CPU · 1 GB, gateway 1 CPU · 768 MB, eureka 0.5 CPU (CPU 주기 100 ms 기본값)
- 워크로드: k6 `shared-iterations` — 500 VU 로 주문 **50,000 건 버스트**
- 반복 단위: `cart_add → order` (VU:유저 1:1, VU:상품 1:1)
- 시드: customer 1,000 (verify=true, balance_history 초기 행 포함), product 100 × product_item 5 (재고 1M)

## 측정 절차

각 N 마다 [README](../README.md) 의 실행 절차 1~11 을 그대로 반복했다.

1. `docker compose down -v` — Redis 카트·DB 상태 완전 초기화
2. 스택 기동 → `db-seed` 완료(`exit 0`) 확인
3. **Eureka registry 폴링** — `order-api` 인스턴스가 N 개 UP 이고 gateway 라우팅이 살아날 때까지 대기
4. **워밍업 런 2 만 건** (결과 버림) — JIT · HikariCP · Hibernate 캐시 예열
5. **SAGA 정지 대기** — `orders.PENDING = 0` 까지
6. 모니터링 시작 → **본 측정 5 만 건**

## 자원 사용

`shared-iterations` 는 공용 반복 풀이 비면서 동시성이 500 → 0 으로 떨어지는 꼬리가 있고, 모니터링 창이
런보다 길면 유휴 구간까지 평균에 들어간다. 아래 **부하 중 avg** 는 CPU ≥ 100 % 인 샘플만 평균한 값이다.

> p95 는 쓰지 않는다. [analyze_monitoring.py:62](../analyze_monitoring.py#L62) 의 `vals[int(n*0.95)]` 는
> 보간 없는 인덱싱이라 표본이 적으면 마지막 원소를 가리킨다 — 2 대(n=19) · 4 대(n=22) 에서는
> p95 가 사실상 max 다. 표본 수에 무관한 **부하 중 avg 와 max** 로 비교한다.

## 핵심 발견

### 1. LB 분배 메커니즘 정상 동작 — 두 독립 지표로 교차 검증

- **인스턴스 간 CPU 편차 ±0.5 ~ 1.5 %** (통과선 ±10 %)
- **`Threads_connected` = 10N + 1** (11 / 21 / 41) — HikariCP 기본 풀 10 이 인스턴스마다 lazy-init 됐다는 것은
  모든 인스턴스가 실제로 트래픽을 받았다는 뜻이다. CPU 와 독립된 지표라 교차 검증이 된다.

ADR-005 의 핵심 가정 "`lb://` 가 N 인스턴스에 round-robin 분배" 는 **정상 동작 확인**.

### 2. 1 → 4 가 선형에 가깝게 확장된다 (효율 87.8 %)

소진 시간 279.2 → 150.2 → 79.5 s, k6 주문 처리량 179.1 → 332.9 → 628.7 /s (×1.86, ×1.89).
인스턴스 증설이 실제 처리량으로 그대로 전환되고 있다.

### 3. ⭐ 꼬리 지연이 증설로 붕괴한다 — 병목은 CPU 포화 큐잉

가장 뚜렷한 결과다.

| 구성 | p95 | p99 | max | p99 / p95 |
| --- | --- | --- | --- | --- |
| 1 대 | 1,307.0 ms | **14,139.9 ms** | 58,566 ms | **10.8×** |
| 2 대 | 894.6 ms | 5,468.4 ms | 31,795 ms | 6.1× |
| 4 대 | 726.6 ms | **1,005.3 ms** | 2,152 ms | **1.4×** |

1 대에서는 상위 1 % 가 14 초, 최악 58.6 초까지 벌어지는데 **4 대에서는 꼬리가 사실상 사라진다**
(p99 −92.9 %, max −96.3 %). p95 는 −44.4 % 만 줄어드는 것과 대비된다 — 증설이 개선하는 것은
중앙값보다 **꼬리**다.

지연은 **전부 서버 처리 구간**에 있다. 연결 수립·전송은 어느 구성에서도 정상이다.

| 항목 (1 대) | p99 | max |
| --- | --- | --- |
| `http_req_waiting` (서버 처리) | **14,139.9 ms** | **58,879.9 ms** |
| `http_req_blocked` | 0.02 ms | 50.6 ms |
| `http_req_connecting` | 0.00 ms | 43.2 ms |
| `http_req_sending` | 0.07 ms | 150.0 ms |
| `http_req_receiving` | 5.97 ms | 103.0 ms |

k6·도커 브리지·커넥션 수립이 아니라 **애플리케이션 처리 시간**이며, 증설로 해소된다는 점에서
고정된 직렬 구간이 아니라 **CPU 포화 상태의 큐잉**이다. 자원 표가 이를 뒷받침한다 —
1 · 2 대는 orderApi 가 CPU 한도의 101 % · 102 % 로 완전히 포화돼 있고, 꼬리가 사라지는 4 대에서
비로소 92 % 로 내려온다.

### 4. 4 대에서 병목이 orderApi 를 떠나기 시작한다

| | 1 대 | 2 대 | 4 대 |
| --- | --- | --- | --- |
| orderapi 부하 중 avg (한도 200) | **201.2** 🔥 | **204.9** 🔥 | 183.1 |
| gateway max (한도 **100**) | 38.4 | 63.7 | **89.9** 🔥 |
| mysql-order max | 63.4 | 113.8 | **174.7** |

orderApi 가 한도에서 내려오는 대신 **gateway 가 1 CPU 한도의 90 % 에 닿는다.** 트래픽이 전부
단일 gateway 를 통과하므로, 인스턴스를 더 늘리면 다음 한계는 gateway 일 가능성이 높다.
효율이 93.0 % → 87.8 % 로 소폭 꺾이는 것도 이 지점과 맞물린다.

## 측정의 한계

- **구성당 단일 런** — 같은 바이너리·같은 절차의 직전 회차(`0f48c60`)와 비교하면
  **소진 시간·CPU·MySQL 처리량은 잘 재현되지만(1 대 소진 272.8 → 279.2 s, MySQL 2,891.5 → 2,904.8 q/s,
  orderapi CPU 212.9 → 210.5) 지연 분포는 재현되지 않았다**(1 대 p99 1,833 → 14,140 ms).
  지연 값은 회차 간에 비교하면 안 된다.
- **모니터링 표본이 적다** — 실측 샘플 간격이 5 초 설정과 달리 약 7.8 초(`docker stats` 왕복 시간)라
  4 대 런은 부하 구간 샘플이 8 개뿐이다. 각 샘플도 7.8 초 구간의 평균이 아니라 데몬 수집 주기(약 1 초)
  기준의 스냅샷이므로, 샘플 사이 구간은 관측되지 않는다.
- **4 대 CSV 에 유휴 구간이 섞였다** — 모니터가 런 종료 후 64 초를 더 기록해 전체 창 평균이 크게
  희석된다(orderapi 전체 창 avg 68.6 vs 부하 중 avg 183.1). 이 리포트가 부하 중 avg 를 쓰는 이유다.
- **kafka CPU 는 신뢰하지 않는다** — 모니터링 창이 런 길이에 묶여 있어 비동기 백로그 처리 구간이
  구성마다 다르게 잘린다.
- **SAGA 완료 시간을 재지 않는다** — 이 하네스는 접수(HTTP 200 = PENDING 생성) 응답만 측정한다.
  본 측정 직후 PENDING 은 1 대 48,913 / 2 대 49,029 가 남아 있었다. 접수가 완료보다 훨씬 빠르며
  이 구간은 ADR-005 범위 밖이다.

## 하네스 결함 (측정 중 발견 · 수정)

모두 **k6 또는 스크립트가 정상으로 보이는 상태에서 조용히 측정을 무효화**하고 있었다.

| 결함 | 증상 | 수정 |
| --- | --- | --- |
| 장바구니 껍데기 누적 | `removeZeroCountItems` 가 아이템이 빈 `Cart.Product` 를 안 지워 카트가 무한 누적. `refreshCart` 가 매 주문 전 상품을 조회해 **주문당 쿼리가 25 → 113 으로 증가**. 20 분 런에서 qps +92 % | k6 상품 선택을 VU 고정으로 (`35cc0d0`) |
| 시드 `balance_history` 누락 | 잔액 검증이 `customer.balance` 가 아니라 `customer_balance_history` 최신 행을 읽는데 시드가 그 행을 안 만들어 **SAGA 결제가 전건 실패**. 주문 10,000 건 전부 FAILED 인데 k6 는 `order fail 0.00%` 보고 | 시드에 초기 행 추가 (`b785044`) |
| `db-seed` 테이블 레이스 | 대기 조건이 `customer`/`product` 만 폴링하는데 `order.sql` 이 `outbox_events` 도 건드려, Flyway 가 만들기 전 시작하면 `exit 1`. 상품이 없어 `cart_add` 전건 실패인데 주문 요청 자체가 0 건이라 실패율이 0 % 로 보고 | 시드가 건드리는 테이블 전체 대기 (`2e31410`) |
| `parse_results.py` 무효 런 통과 | 무효 판정이 `p95 is None` 인데, 중단된 런의 `order_create` 서브메트릭은 no-op threshold 로 생성되어 값이 `None` 이 아니라 **0**. 중단된 런이 **"p95 0 ms" 라는 최고 성적**으로 표에 실릴 수 있었다 | 반복 완료 수(`iterations.count`)로 판정 |
| `monitor-stats.sh` CRLF | Git for Windows 의 `core.autocrlf=true` 가 체크아웃 시 CRLF 를 넣어 bash 가 `\r` 을 값의 일부로 읽음 — `RESULTS_DIR="results\r"` 로 CSV 경로가 깨지고 스크립트가 실행 자체를 못 함 | `.gitattributes` 에 `*.sh text eol=lf` 고정 |
| CPU p95 가 max 로 붕괴 | `vals[int(n*0.95)]` 가 표본이 적으면 마지막 원소를 가리켜, 2 대(n=19) · 4 대(n=22) 의 "p95" 가 실제로는 max. 1 대(n=36) 만 진짜 p95 라 구성 간 비교가 상향 편향됐다 | 리포트를 부하 중 avg + max 기준으로 전환 |

## 이전 회차 기록 (4 인스턴스 기준 자원 튜닝 · 미재현)

직전 회차(`0f48c60`)에서 4 인스턴스를 기준으로 수행한 자원 튜닝 실험이다.
**이번 회차에서 재현하지 않았고, 그 회차의 4 대는 소진 124.2 s 로 이번(79.5 s)과 달랐다.**

| 조치 | p95 변화 |
| --- | --- |
| CPU 주기 100 → 20 ms | **+33.0 %** (스로틀 7~10 % → 49~66 %) |
| CPU 주기 100 → 200 ms | −2.5 % (노이즈 안) |
| gateway 1 → 2 CPU | −6.7 % (노이즈 안) |
| HikariCP 풀 10 → 30 | +17.0 % |
| orderapi 2 → 3 CPU | +22.7 % (스로틀은 0 % 로 소멸) |

> gateway 1 → 2 CPU 는 당시 −6.7 % 로 노이즈 안이었으나, 이번 회차에서 4 대의 gateway 가
> 한도의 90 % 에 닿는 것이 확인됐다(핵심 발견 4). **지연이 아니라 소진 시간 기준으로,
> 8 대 이상 구성에서 재시험할 가치가 있다.**
