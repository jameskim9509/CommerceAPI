## 1. 헤드라인

```
N = ① + ② + ③ + ④ + ⑤ + 카오스잔여(T1~T4)
```

| 성분 | 무방어 `A` | 방어 `a` | 비고 |
| ---- | ---------: | -------: | ---- |
| ① 중복 주문/결제 | 20 | **0** | 10/10 런 0 |

| **총 위반 `N`** | **66,624.5** | **529** | 범위 [61,666..73,485] → [90..2,280] |

이는 방어가 T1~T4 를 막아서가 아니라 **⑤ 중복 처리가 억제되면서 파이프라인 백로그가 얕아져 T4 로그 전소
순간에 유실되는 in-flight 이벤트가 줄었기 때문**이다(§4.3).

### 2.2 arm 전환 검증 — 소스가 아니라 거동으로 확인했다

이미지와 소스가 어긋나도 산출물로는 구별되지 않는다. `.dockerignore` 가 `qa/` 를 제외하므로
하네스 리비전은 이미지와 인과가 없고, 브랜치만 봐서는 판별할 수 없다.

**실제로 이 사고가 발생했다**: treatment 이미지 빌드가 `gradlew` CRLF 로 `exit 127` 로 죽었는데
이전 control 이미지가 그대로 남아 있었다. 그 상태로 배치를 돌렸다면 `T-run*` 이 control 재측정이 되고
`N→r` 이 1:1 로 나와 "방어 효과 없음"이라는 정반대 결론이 아무 흔적 없이 남았을 것이다.

이미지를 명시 삭제 후 재빌드하고, 배치 전 스모크로 **실행된 컨테이너의 거동**을 확인했다:

| 판별 신호 | control 스모크 | treatment 스모크 |
| --------- | -------------- | ---------------- |
| `processed_events` 행수 | `orders[-] user[-]` | `orderapi-stock=1997 \| userapi-payment=1997` |
| `a_T2T4` | `n/a` 강등 | 0 건 (실수치) |
| ⑤ 중복 처리 | 2,143 | 0 |
| `v2b` 이중 차감 | 11 | 0 |
| `ProductItem.version` | 0 (필드 없음) | 135 |
| `status` 분포 | CONFIRMED 만 | CONFIRMED + FAILED 28 (보상 경로 작동) |

또한 각 T-run 의 `processed_events` 가 컨슈머별로 8만 행대로 채워져 있음을 사후 확인했다
(T-run1 `orderapi-stock=83030 | userapi-payment=83279`).

> 재발 방지로 `verify` 가 `processed_events` 행수로 arm 을 실측 판정해 헤더에 출력하고,
> `aggregate` 가 라벨과 다른 런을 ⚠ 로 표시해 집계에서 제외하도록 커밋했다(`ca5aae1`).

> 본 측정의 arm 확인은 위 스모크와 `processed_events` 사후 확인으로 대체했다.

## 4. 카오스잔여 `r` = 529 는 무엇인가

방어 arm 의 `r` 은 **전량이 카오스잔여**다(①~⑤ 가 10/10 런 0 이므로). 5종 방어의 대상이 아닌
**주변 장애 T1~T4 의 몫**이며, 무방어 arm 에도 19,842 만큼 존재한다.

```
카오스잔여 = max(0, v3a − ③미보상) + a_T1
```

| 성분 | 무방어 median | 방어 median | 성격 |
| ---- | ------------: | ----------: | ---- |
| `v3a` 미착지 주문 | 20,516 | 526.5 | T2 드롭 / T4 로그 전소로 이벤트가 유실된 주문 |
| ㄴ 그중 hop1 유실 | 22,013\* | 24 | 주문 생성 이벤트는 발행됐는데 하류가 없음 (T4 지문) |
| `a_T1` 공짜 주문 | 0 (구조적) | 1 | 확정된 주문인데 환불됨 — **방어를 켰기 때문에 생기는 위반** |
| 돈 누수 | 140,044,500원 | 1,359,500원 | 위 잔여의 화폐 표현 (순액) |

\* C-run1~3 실측(22,333 / 15,000 / 21,692)의 중앙값. hop1 유실은 `v3a` 의 부분집합이라 따로 더하지 않는다.

**`③미보상`을 빼는 이유**: 재고 부족으로 실패한 주문은 롤백되어 미착지(PENDING) 상태로 남으므로
`③미보상 ⊆ v3a` 다. 실측(C-run1)에서 `v3a` 27,478 ⊇ hop1유실 22,333 + ③미보상 1,088 이 확인됐다.
빼지 않으면 ③ 이 두 번 세진다. `a_T1` 은 대상이 CONFIRMED 라 `v3a`(PENDING/PAID)와 서로소이므로 그대로 더한다.

### 4.1 `a_T1` — 방어가 만든 위반

방어 arm 에만 0~5건 존재하고 무방어 arm 은 **구조적으로 0**이다(환불 코드 자체가 없어 그 상태가
성립하지 않는다). 기전은 재고예약(`REQUIRES_NEW`) 커밋 ↔ dedup 마커 커밋 창이 T1/T2 로 파열된 뒤
재배달이 일어나 같은 주문에 환불 요청이 중복 발행되는 것이다. dedup 이 `eventId` 기준이라 서로 다른
`eventId` 의 환불 요청은 각각 통과해 중복 환불된다.

전 런에서 `부당환불 = a_T1` 로 일치했다(중복환불 성분 0) — 즉 **실패한 주문에 두 번 갚은 사례는
없었고, 전부 확정된 주문에 갚은 형태**였다.

**보상 트랜잭션은 "잃는 위반"을 "주는 위반"으로 바꾼다.** 140,044,500원 → 1,359,500원은 명백한
개선이지만 0 은 아니며, `Order.markFailed()` 가 CONFIRMED 를 거부하는 설계가 그 잔여의 원인이다.
"확정 후 환불 도달" 케이스를 어떻게 처리할지는 별도 ADR 감이다.

### 4.2 돈 누수는 순액이라 성분이 상쇄된다

미보상·이중 결제 미환불은 (+), 부당환불은 (−) 로 한 숫자 안에서 상쇄된다. 방어 arm 의 1,359,500원은
순액이므로 **미보상이 그만큼 작다는 뜻이 아니다.** 성분별 크기는 건수로 읽어야 한다.

### 4.3 방어 arm 의 카오스잔여가 37배 작은 이유 — 방어가 T1~T4 를 막아서가 아니다

무방어 19,842 vs 방어 529. 카오스는 양 arm 에 동일하게 주입됐으므로(20/20 런 `T2=1 T3=1 T1=1 T4=1`)
이 차이는 방어가 주변 장애를 막았기 때문이 아니다.

**기전은 백로그 깊이다.** 무방어 arm 은 ⑤ 중복 처리로 이벤트를 약 2배 만들어내므로 파이프라인에
상시 깊은 백로그가 쌓인다. T4 가 카프카 로그를 소각하는 순간 그 백로그 전체가 유실되므로 잔여가 커진다.
방어 arm 은 dedup 이 중복을 처리 단계에서 막아 백로그가 얕고, 따라서 소각 순간 잃는 양도 적다.

즉 **⑤ 방어의 2차 효과가 T4 피해를 줄인 것**이며, 이는 리포트가 주장하는 "5종 방어의 효과"에
포함시켜도 되는 인과다. 다만 "방어가 T1~T4 를 막았다"고 쓰면 틀린다 — **미검증**이며 직접 근거는
백로그 깊이 대조(`s_pd/s_oc` 비율)뿐이다.

## 5. 이번 측정에서 확정된 것

### 5.1 ⑤ 는 카오스 없이도 대량 발생한다 — `OutboxPoller` 다중 인스턴스 경합

무카오스 스모크(2,000건, 카오스 0종)에서 `s_pd/s_oc` = **4,136/1,993 = 2.03배**가 나왔다.
카오스가 없으므로 Kafka 재배달·리밸런스로는 설명되지 않는다.

코드 확인 결과 `OutboxEventRepository.findTop100BySentAtIsNullOrderByCreatedAtAsc()` 에
**비관적 락·`SKIP LOCKED`·인스턴스 샤딩이 전부 없고**(`grep` 0건), `OutboxPoller` 가 `@Scheduled` 라
orderApi 4대 + userApi 2대에서 **각각 독립 실행**된다. 잠금 없는 읽기라 여러 인스턴스가 같은 미발행
행을 읽고 각자 Kafka 로 보낸 뒤 `markSent` 를 덮어쓴다.

무방어 arm 의 ⑤ = 45,529건(전체 위반의 97%)은 이 경합과 Kafka at-least-once 가 섞인 값이며
**둘의 비율은 분리되지 않았다(미검증)**. 정합성 자체는 방어 arm 에서 dedup 이 흡수해 0 이지만,
중복 발행분만큼 파이프라인 처리량을 버리고 있다는 뜻이므로 QA 와 별개로 확인할 가치가 있다.

### 5.2 ③ 이 무방어 arm 에서 처음 관측됐다

기존 지표(`d3`, 환불 이력 기반)는 무방어 arm 에서 환불 코드가 없어 구조적 0 이었다. SRF 를 발행하는
`StockConsumer` 는 arm diff 6파일 밖이라 **무방어 arm 도 환불 요청 이벤트는 정상 발행**한다는 점을
이용해, 발행측 payload 의 `reason` 을 필터링하는 `d3p` 로 바꿔 중앙값 776.5 를 얻었다.

`reason` 필터가 필수임도 확인됐다 — 스모크에서 SRF 5,271건이 **전부 "허용되지 않은 주문 상태 전이"**
사유였고, 필터가 없었다면 이 헛 요청이 통째로 ③ 으로 잘못 계상됐을 것이다.

### 5.3 무음 0 함정이 실재함을 실증했다

합성 행을 넣어 같은 쿼리를 charset 지정 유무만 바꿔 실행했다:

```
q_order_u (--default-character-set=utf8mb4) : 1
q_order   (charset 미지정)                   : 0
```

`q_order_u` 를 쓰지 않았다면 **③ 이 전 런에서 조용히 0** 으로 나왔을 것이다. `payload` 컬럼 charset 이
`utf8mb4` 임도 함께 확인했다(그동안 미검증 항목).

## 6. 측정 자체의 한계 (자가 비판)

### 6.1 ② 는 하한이다

hot SKU 재고 1,000 대 수요 약 8,000 이라 부하 시작 약 154초(런의 14%)에 재고가 완전히 소진되고,
그 뒤로는 재고 가드에 걸려 초과판매가 더 일어날 수 없다. 실측 74.5는 "이 시드 조건에서 관측된 양"이지
방어 부재의 참값이 아니다.

### 6.2 ④ 는 탐지가 정확하지만 크기가 ⑤ 에 종속된다

무방어 arm 은 이벤트 중복 처리 때문에 잔액 변경 호출이 배로 늘어 경합 기회가 그만큼 커진다.
중앙값 357 중 ④ 자체와 ⑤ 가 증폭시킨 몫은 갈리지 않는다.

### 6.3 ⑤ 는 중복 "처리" 계수이지 "배달" 계수가 아니다

`outbox_events` 는 발행을 기록하지 배달을 기록하지 않는다. **방어 arm 의 0 은 "배달이 없었다"가 아니라
"처리가 없었다"** 는 뜻이다 — 배달은 양 arm 에 동일하게 일어나고 dedup 이 처리 단계에서 막는다.
리포트를 "중복 **배달** 45,529 → 0" 으로 인용하면 Kafka 가 arm 별로 다르게 동작한 것처럼 오독된다.

### 6.4 ⑤ 의 역순 축은 계수하지 않았다

순서 역전은 **어느 주문이 한정 재고를 가져가느냐(분배)** 를 바꿀 뿐 위반 총량을 바꾸지 않고,
이를 거부하는 `Order` 상태 전이 가드는 양 arm 이 같은 코드다. 따라서 `N→r` 에 기여하지 않아
별도 계수기를 두지 않았다.

역순이 중복 없이도 발생한다는 점은 별개로 확인됐다 — 메시지 키가 `eventId`(UUID) 라 같은 고객의 두
주문이 다른 파티션에 떨어지고, 컨슈머 다중 인스턴스가 동시에 드레인하면 발행 순서와 처리 순서가
어긋난다. **이 경로는 재배달 0 인 상태에서도 성립하므로 "역순 ⊆ 중복" 은 참이 아니다(미검증 반례).**

### 6.5 주변 장애 T1~T4 는 개별 귀속되지 않았다

T2(재시도 소진 드롭)와 T4(kafka 로그 전소)는 최종 DB 상태가 동일해 `v3a` 안에서 분리되지 않는다.
`a_T1` 도 T1 고유 지문이 아니며 T2·리밸런스가 같은 상태를 만든다. 확정 귀속은 `FAULTS` 절제 런이
필요하나 **통합 시나리오의 전제(5+4 장애 동시 발화)를 깨므로 수행하지 않았다.**

### 6.6 `N` 산식이 재정의됐다

이전 리포트의 `N` 은 구산식(`v1 + v2a + max(v2b,v2c) + v3a + v3b + v3c + v3e`, 행/수량/주문 혼합)
값이다. 현행 `N` 은 **의도된 장애 ①~⑤ 위반 건수 + 카오스잔여**의 합이며 **같은 이름의 다른 지표다.**
이전 값과 직접 비교할 수 없어 기존 리포트는 삭제했다.

**본 리포트의 `N` 은 산출물의 성분에서 재계산한 값이다.** 20런을 돌린 시점의 `verify` 는 카오스잔여를
포함하지 않는 산식(`①~⑤` 만)을 쓰고 있었다. 성분(`①~⑤`·`v3a`·`a_T1`)은 모든 산출물에 그대로 기록돼
있으므로, 산식만 바꿔 재계산했고 **재측정은 하지 않았다.** `aggregate-runs.sh` 도 출력 라인이 아니라
성분에서 `N` 을 계산하도록 바꿔, 구·신 산출물이 같은 산식으로 집계된다.

`results/<LABEL>-verify.txt` 의 `총 위반 건수 ... N =` 라인은 **측정 당시의 옛 산식 값**이다.
원자료를 사후 수정하지 않는다는 원칙에 따라 그대로 두었으므로, 리포트·`AGGREGATE` 의 `N` 과 다르다.
다음 측정부터는 `verify` 가 카오스잔여를 포함한 `N` 을 직접 출력한다.

### 6.7 arm 판별 가드가 본 측정에는 미적용

§2.2 의 verify/aggregate 가드는 본 20런이 시작된 뒤 커밋됐다. 본 측정의 arm 확인은 스모크 6신호와
각 런의 `processed_events` 사후 확인으로 대체했으며, 다음 측정부터는 산출물 자체가 arm 을 명시한다.
