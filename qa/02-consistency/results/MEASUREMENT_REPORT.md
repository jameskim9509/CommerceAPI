## 2. KPI

### 2.1 ★ N 산식의 이중 계상 정정

**이 20런을 측정할 당시의** `verify-consistency.sh` 는 `N = v1 + v2a + v2b + v2c + v3a + v3b + v3c + v3e` 로
**v2b 와 v2c 를 둘 다 더했다**. hot 재고가 0 으로 클램프되면 `차감량 = init = 1000` 이 되어
`v2b = CONFIRMED수량 − 1000 = v2c` 가 구조적 항등이 되고, 실제로 **control 10/10 런에서 v2b = v2c** 다
(91/108/105/98/110/109/122/115/113/120).
같은 초과판매가 N 에 두 번 들어간다. treatment 는 v2c=0 이라 영향이 없으므로 **이 이중 계상은 control 만 부풀린다.**

→ 아래는 중복분을 제거한 **N′ = N − v2c** 를 주 지표로 쓴다. 원 산식의 N 도 병기한다.

> **산식은 이후 수정됐다** (커밋 `386f337`, 양 arm 체리픽). 현재는 `max(v2b, v2c)` 로 합쳐
> 두 신호를 다 살리되 한 번만 센다 — 즉 **다음 런부터는 verify 가 출력하는 N 이 곧 여기서 말하는 N′** 다.
> `results/` 에 남아 있는 이 20런의 `*-verify.txt` 는 수정 전 산식으로 찍힌 값이므로, 그 파일들의
> "집계 KPI ... N =" 줄과 이 리포트의 N′ 는 control 에서 v2c 만큼 다르다(treatment 는 동일).
> `aggregate-runs.sh` 가 생성한 `C2-AGGREGATE.md` 도 수정 전 N 기준이다.

### 2.4 ★ money_leak 의 종속성 — 독립 축이 아니다

control 에서 다음이 **대수적 항등식**으로 성립한다(`s_pf = 0`, `s_oc = CONFIRMED + PENDING` 이므로):

```
|o_L1| + v3a  =  (s_pd − s_oc) + PENDING  =  s_pd − CONFIRMED
money_leak    ≈  (s_pd − CONFIRMED) × 평균 주문가
```

10/10 런에서 확인했다 — C2-run1: 47,521 + 778 = 48,299 = 111,877 − 63,578,
C2-run6: 47,551 + 288 = 47,839 = 115,140 − 67,301, C2-run10: 57,031 + 230 = 57,261 = 129,512 − 72,251.
나눈 값은 2,933~2,946원으로 평균 주문가(2,972~2,978원)와 거의 일치한다.

그리고 이 합의 **98.4%가 |o_L1|** 이다(C2-run1: 47,521 / 48,299).
→ **money_leak 의 362.9배 분리는 사실상 ⑤(이벤트 중복 처리)를 돈 단위로 재표현한 것이다.**
money_leak 을 "방어 5종의 종합 효과"로 읽거나, o_L1 과 나란히 독립 근거로 세면 같은 사건의 이중 계상이 된다.

독립적으로 분리되는 축은 **v1(①) · v2c(②) · d4b(④) · o_L1 부호(⑤)** 네 개이고,
money_leak 은 그 중 o_L1 의 종속 변수다.

## 4. 장애별 귀속

> ★ **control 의 구조적 0 은 "장애가 없었다"가 아니라 "관측 불가"다.**
> 방어 코드와 계측기가 같은 코드이기 때문이다 — `RefundConsumer` 본문 = 방어 ③ 이자 환불 이력 계측기,
> `processed_events` 기록 = 방어 ⑤ 이자 마커 계측기, `Customer.@Version` = 방어 ④ 이자 version 계측기.
> control 에서 0 이 되는 지표: `a_T1` · `T1 지문` · `환불 총건수` · `FAILED` · `d2` · `d3` · `a_T2T4`(n/a) · `d5`.
> 이 여덟 개는 arm 비교에 **쓸 수 없다.**

### 4.1 ① 중복 주문/결제 (진입 멱등성)

| | 값 |
|---|---|
| 지표 | `v1` = 같은 멱등키로 2건 이상 생성된 초과분. `a_T3`·`d1` 이 10/10 런 v1 과 동일값(3중 검산) |
| control | med **90** [67 .. 134], mean 91.6 — 10/10 런 > 0 |
| treatment | **0** — 10/10 런 |
| U | 0 (완전 분리, 간격 67) |
| 신뢰도 | **high(존재)** / **low(control 크기)** |

**크기가 low 인 이유(정정):** k6 재전송 overlay 는 첫 POST 가 200 일 때만 발화하고, 그 시점엔 카트가 이미 소비됐다.
스크립트 자신이 `timeout_retry_non2xx` 주석에 non-2xx 를 "409(방어 ON) 또는 **400(카트 소비됨)**"이라 적어 두었다.
control 의 replay non-2xx 1,300~1,482건은 '중복이 차단된 것'이 아니라 **카트가 없어 400 으로 실패한 것**이다.
실제로 control 의 v1 은 k6 `replay_2xx` 와 거의 같은 수다 — C2-10 68 vs 68, C2-7 67 vs 64, C2-2 91 vs 89, C2-6 134 vs 119.
→ ① 주입 1,388~1,550건 중 **카트 소비 경합에서 이긴 4~9%만이 위반으로 관측 가능**했다. control v1 은 하한이다.
(treatment 의 replay_2xx 99%대는 '캐시된 응답 반환', control 의 4~8%는 '중복 주문 생성'으로 **의미가 다르다** —
두 비율을 나란히 놓고 "독립 지지"라 부르면 안 된다. 같은 사건을 클라이언트에서 센 것이다.)

부수적 하한 요인: '생성 − 의도 차분'이 20/20 런 0 으로 클램프됐다(의도 > 생성이라 음수가 0 으로 잘림).

### 4.4 ④ 잔액 Lost Update

| | 값 |
|---|---|
| 지표 | `d4b` = 원장 체인 끊김(`current_money ≠ 직전 행 change_money`). 양 arm 모두 원장 테이블이 있어 **동일 쿼리 = arm 중립** |
| control | med **377** [276 .. 415], mean 365.8 — 10/10 런 > 0 |
| treatment | **0** — 10/10 런 |
| U | 0 (완전 분리, 간격 276) |
| 신뢰도 | **high(존재)** / **medium(크기)** |

기전 확인: `CustomerBalanceHistoryRepository.findByCustomerIdRecent` 가 `where h.id = (select max(h2.id) …)` 이고
d4b 체인 검사도 같은 `h.id` 로 LAG 를 건다. 링크가 끊기려면 **두 트랜잭션이 같은 max(id) 를 읽는 사건이 필수** —
정의상 Lost Update 다. 순수한 순서/타임스탬프 아티팩트로 끊길 경로는 찾지 못했다.

**크기를 medium 으로 낮춘 이유:** control 은 `changeBalance` 호출이 115,140~129,512회로
treatment(약 61,176~76,000)의 **약 1.8배**이고 대상은 같은 300명 풀이다. 동일 행 경합 기회 자체가 2배에 가까우므로
377 대 0 의 '크기'에는 @Version 부재와 ⑤ 제거로 늘어난 경합량이 섞여 있다.

`ledger_gap`(원장 최신합 vs `customer.balance` 합)은 control 도 10/10 런 0 이다. 이는 "피해가 장부상 형식 문제"라는 뜻이 아니라
**파생 캐시가 항상 최신 원장 행과 일치하므로 캐시 비교로는 ④ 를 탐지할 수 없다**는 뜻이다.
금액 효과는 money_leak 에 음(무에서 창조) 방향으로 흡수돼 있다 — control 10/10 런에서
`money_leak ÷ (s_pd − CONFIRMED)` 가 평균 주문가보다 1.0~1.3% 낮다(C2-1 2,946 vs 2,978 / C2-6 2,933 vs 2,972).
방향은 ④ 와 정합하나, hot/normal SKU 가격 믹스 차이로도 같은 부호가 나올 수 있어 **확정하지 않는다.**

`d4`(참고값)는 control 10/10 런 300명이지만 control 에는 @Version 필드가 없어 탐지력이 없다 — ④ 신호로 읽으면 안 된다.

### 4.5 ⑤ 이벤트 중복 처리 (역순은 미측정)

| | 값 |
|---|---|
| 지표 | `o_L1 = s_oc − s_pd − s_pf` 의 음수 절대값 = 중복 처리 하한. `o_L2` 는 체인 2단계 전파 확인 |
| control | \|o_L1\| med **51,513** [47,521 .. 57,031] — 10/10 런 음수. o_L2 도 10/10 런 음수(−30,790 ~ −39,002) |
| treatment | 음수 런 **0건** — 6/10 런 o_L1 = 0, 4런(43/325/394/490)은 **유실 방향 양수** |
| U | 0 (부호 완전 분리) |
| 신뢰도 | **high(방향·존재)** / **low(기전)** |

대안 원인 배제: `s_oc` 가 20/20 런에서 생성 주문 수와 정확히 일치해 outbox 퍼지·런 간 누적 오염이 배제되고,
payment-deducted 를 내는 경로는 order-created 소비뿐이며 `s_pf` 는 10/10 런 0 이라
'한 order-created 가 두 후속을 낸다'는 경로도 없다.

**기전은 미확인이다.** control 의 `s_pd / s_oc` = **1.70 ~ 1.79**(주문 1건당 평균 1.75회 처리)인데,
18.5분 런에 카오스가 4회뿐인 조건에서 재배달만으로 70~79% 중복이 나오는 것은 주입된 폴트만으로 설명되지 않는다.
컨슈머 리밸런스 재배달인지, outbox 릴레이가 `sent_at` 마킹 실패로 같은 행을 재발행한 것인지,
DefaultErrorHandler 재시도가 후속 이벤트를 여러 번 낳은 것인지 이 산출물로는 **구분되지 않는다**(셋 다 ⑤ 종류라 귀속 방향은 안전).
컨슈머 로그의 리밸런스 횟수 또는 릴레이 재발행 카운터 하나면 구분 가능하다.

**o_L1 은 순합이다.** 유실과 중복이 상쇄되므로 \|o_L1\| 은 control 중복의 하한일 뿐이고,
반대로 treatment 에 음수 런이 없다는 것이 'treatment 중복 처리 0' 을 증명하지 않는다
(실제로 treatment 양수 4런 run1/3/8/9 는 T4 유실이 큰 런과 정확히 겹친다).
또 이 지표는 중복/유실만 재고 **역순(순서 뒤바뀜)은 전혀 측정하지 않는다.**

### 4.6 T1 — orderapi SIGKILL

| | 값 |
|---|---|
| 지표 | `a_T1`(CONFIRMED 인데 환불된 주문) + T1 지문(`reason=허용되지 않은 주문 상태 전이입니다.`) |
| control | **구조적 0 = 관측 불가** — 환불 이력이 없어 지문이 남지 않는다 |
| treatment | med 1 [0 .. 5], mean 1.6. 10런 중 3런(run8/9/10)은 0 |

검산식 정정: 10/10 런에서 성립하는 항등식은 **`a_T1 = 환불 총건수 − (d2 + d3)`** 다(20런 검증 완료).
`환불총건수 − FAILED` 가 아니다 — `(d2+d3) − FAILED` 는 3런에서 0 이 아니고(T2-2 = 2, T2-5 = 2, T2-10 = 3),
그 값은 **환불은 집행됐으나 `markFailed` 가 착지하지 못한 주문 수**(payment-reverted 잔여)와 정확히 일치한다.

T1 의 서명은 '무에서 돈 창조'(money_leak 음수 기여)인데 treatment money_leak 은 10/10 런 전부 양수다.
a_T1 이 최대 5건이라 T2/T4 소실(수백~수천 건)에 완전히 묻혔다. **부호가 뒤집힌 런은 20런 중 0건.**

### 4.7 T2 / T4 — PENDING 시각 클러스터 귀속

**방법**: PENDING/PAID 생성시각 분(minute) 히스토그램에서 주입시각 M 기준 `[M−2, M+1]` 창 버킷 합.

| **T4 몫**(kafka 로그·오프셋 전소) | med 200 [8 .. 825], 합 2,821 = 잔여의 **99.7%** | med 319 [91 .. 1,135], 합 4,226 = 잔여의 68.1% | **38** (유의차 없음) |

귀속 방법을 뒷받침하는 사실:
- 20/20 런에서 창별 합 + 기타 = `v3a` 와 정확히 일치. 창 밖 '기타' 버킷은 전 20런 통틀어 **2행뿐**
  (T2-run1 07:30=1 — 부하 시작 직후 / C2-run9 15:12=1 — T4 창 +2분).
- **T1·T3 근처 버킷은 20/20 런 전부 0.** T3(FLUSHALL)은 멱등키만 날려 PENDING 을 만들지 않고,
  T1(SIGKILL)은 환불/FAILED 로 착지한다. → PENDING 히스토그램은 사실상 **T2/T4 전용 지표**다.

경계 민감 사례 2건:
- C2-run3 의 `10:45=25` 는 T2 창(M+1)과 T3 창(M−2)에 동시에 걸린다. T3 는 PENDING 생성 기전이 없어 T2 로 귀속(337).
  T3 로 옮기면 312.
- T2-run1 의 `07:43=1` 은 T4 창의 M−1 이라 T4 로 넣었다. 창을 `[M−1, M+1]` 로 좁히면 기타로 빠진다(T4=310).

**T4 몫은 상한값이다** — T1 재기동 완료가 T4 창 시작보다 앞선다(T2-run1: T1 완료 07:41:45 vs T4 창 시작 07:42).
T1 여파로 좌초한 주문은 정의상 T4 몫으로 계상되며, 이 구조는 20/20 런에서 동일하다(실측 영향은 1행).

**⚠ T2 몫 차이의 인과는 확정되지 않았다.** §1.1 대로 두 arm 은 `DefaultErrorHandler`·재시도·DLT 가 **동일**하다 —
'T2 드롭을 막는 방어'는 존재하지 않는다. 더 절약적인 설명이 데이터에 있다: control 은 같은 브로커·DB 로
**1.70~1.79배의 이벤트를 흘렸다**(§4.5). mysql-order 가 10초 멎을 때 좌초하는 건수는 그 순간의 in-flight 깊이에 비례하므로,
⑤ dedup 이 내부 백로그를 1.8배 줄인 결과가 T2 창 PENDING 차이로 나타났을 수 있다.
→ **"방어 5종이 T2 를 전멸시켰다"고 쓰지 않는다.** 두 가설은 `FAULTS=T2` 단독 treatment 런 하나로 구분된다
(방어 효과설이면 0, 백로그설이면 control 보다 낮되 0 은 아님). 검증 전까지 "T2 계열 대책은 불필요" 류의 실무 권고는 내리지 않는다.

## 5. 새 계측기가 해결한 것

### 5.1 ④ 를 처음으로 계수했다 — `d4b`

`2a86a55` 에서 도입. 이전에는 ④ 의 지표가 `d4`(version = history행수 − 1) 뿐이었는데,
treatment 는 history 행 추가와 version 증가가 같은 트랜잭션이라 기대식이 **항등식**이고,
control 은 @Version 필드가 없어 version 0 고정이다 — **양쪽 다 Lost Update 탐지력이 0** 이었다.

`d4b`(원장 체인 끊김: `current_money ≠ 직전 행 change_money`)는 **양 arm 에 같은 테이블·같은 쿼리**로 적용되는
최초의 arm 중립 ④ 지표다. 결과: control 276~415 / treatment 0 (완전 분리, U=0).
④ 가 "재현됐다"고 말할 수 있게 된 것은 이 계측기 덕이다.

### 5.2 ⑤ 를 처음으로 계수했다 — `o_L1` / `o_L2`

`ec3ad50`(head 커밋)에서 도입. 종래의 ⑤ 지표였던 `a_T2T4`·`d5` 는 **`processed_events` 에 의존**하는데
그 테이블 자체가 방어 ⑤ 다 — control 에서는 존재하지 않아 `n/a` 로 강등된다(10/10 런).
즉 **⑤ 는 원리적으로 arm 비교가 불가능했다.**

`o_L1 = s_oc − s_pd − s_pf` 는 `outbox_events` 만 쓰므로 방어 유무와 무관하게 같은 의미를 갖는다.
부호가 정보를 담는다 — 양수 = 하류 유실, **음수 = 같은 이벤트 이중 처리**.
결과: control 10/10 런 음수(−47,521 ~ −57,031), treatment 음수 런 0건. **⑤ 위반이 처음으로 수치화됐다.**
동시에 §2.4 에서 보듯 money_leak 의 98%가 이 값의 화폐 표현임도 이 계측기가 있었기에 드러났다.

### 5.3 ★ T2 는 Hikari `connectionTimeout` 조정 전에는 아예 발화하지 않았다

T2 의 결함 기전은 "Kafka `DefaultErrorHandler`(`FixedBackOff(0L, 9)` = 지연 없이 총 10회)가 재시도를 소진한 뒤
log-and-commit 으로 이벤트를 드롭"이다. 드롭이 나려면 리스너가 **DB 불가 구간 안에서 10회 시도를 전부 태워야** 한다.
1회 시도의 소요 = 커넥션 획득 블로킹 = HikariCP `connectionTimeout`:

| connectionTimeout | 재시도 창 | DB 불가 시간(≈21s: stop 10s + 재기동·크래시 리커버리) | 결과 |
|---|---|---|---|
| 30,000ms (HikariCP 기본, 무설정) | ≈300s ≫ 21s | 첫 시도가 DB 복귀까지 그대로 대기했다 성공 | **예외 자체가 안 남 → 재시도도 드롭도 0** (실측: `T-noT4` 런 v3a=0) |
| **1,000ms** (`DB_CONN_TIMEOUT_MS=1000`, `3e1663d`) | ≈10s < 21s | 10회 소진 후 드롭 | **T2 재현** |

역사적으로 `f426df4`("카오스 앵커를 시간 기반으로 전환")가 정반대 방향으로 튜닝했다 —
T2_DOWN_S 를 25→10s 로 낮춰 DB 불가 시간을 connectionTimeout 안쪽에 넣어 Hikari 타임아웃 0건을 만들었고,
그 결과 **T2 결함이 통째로 잠들어 있었다.** `3e1663d` 이후에야 T2 가 관측 가능해졌다.

→ 그래서 `C-run1`~`C-run3` · `T-run1`~`T-run2` · `T-noT4` 등 **이전 표본은 이번 20런과 조건이 다르며 섞으면 안 된다**
(라벨을 `C2-`/`T2-` 로 분리한 이유). 이번 리포트는 전부 `DB_CONN_TIMEOUT_MS=1000` 표본이다.

### 5.4 T2/T4 를 시각 클러스터로 근사 분리했다

T2 와 T4 는 **DB 지문이 동일**하다(둘 다 PENDING 방치 + 돈 소실). 시간 기반 카오스 앵커(`f426df4`)와
`chaos.log` 의 실제 주입 시각 기록 덕에, PENDING 생성시각 분 히스토그램으로 **근사 분리**가 가능해졌다(§4.7).
20/20 런에서 잔여 질량의 99.9% 이상이 4개 창 안에 설명되고, T1·T3 창은 전부 0 이다.
다만 이것은 **확정 귀속이 아니라 시각 상관에 의한 추정**이다(§6.4).

## 6. 한계

### 6.1 표본 수 · 다중비교

arm 당 n=10. `stats` 수준에서만 14개 지표에 α=0.05 양측 검정을 돌렸고 부하 성립성 쪽에서 3개를 더 돌렸다.
**다중비교 보정은 하지 않았다.** 임계값 23 에 겨우 걸친 결론들 — `v3a`(U=20), `orders_made`(U=21),
`ok_2xx`(U=21), `replays_attempted`(U=22), `CONFIRMED`(U=23, 임계값과 동일) — 은 **어떤 보정으로도 살아남지 않으며,
표본 1개만 바뀌어도 뒤집힌다.** 이들은 '유의'가 아니라 '경계값'으로 읽어야 한다.
`v1`·`v2c`·`d4b`·`money_leak`·T2몫(전부 U=0)과 `N′`(U=10)은 보정 후에도 안전하다.

또 Mann-Whitney 는 확률적 우세를 검정하는 것이지 중앙값 동일성을 검정하는 것이 아니다.
본문의 "중앙값이 낮다"는 표현은 위치이동(location shift) 가정을 추가로 깔고 있다.

### 6.2 변동성의 원인 — T4 백로그

지표별 **범위/중앙값 비**(표준편차÷평균인 변동계수가 **아니다** — 범위는 극단값 1개에 좌우되고 n 이 같을 때만 비교 가능하다):

| 안정적 | | 불안정 | |
|---|---:|---|---:|
| orders_made (C) | 0.118 | v1 (C) | 0.744 |
| o_L1 (C) | 0.185 | N′ (C) | 1.389 |
| money_leak (C) | 0.189 | v3a (C) | 1.890 |
| d2 (T) | 0.200 | d3 (T) | 2.014 |
| v2c (C) | 0.283 | money_leak (T) | 2.949 |
| d4b (C) | 0.369 | N = v3a (T) | 4.085 |

결정론적 경합·보존식 지표(o_L1, v2c, d4b)는 재현성이 좋고, **PENDING 잔여(v3a·N)는 나쁘다.**
원인은 T4 가 단발 이벤트라는 점이다 — kafka 로그·오프셋이 전소되는 그 **순간의 lag(in-flight 깊이)** 이 그대로 잔여가 된다.
treatment 는 잔여의 99.7%가 T4 몫이므로 N 의 산포가 곧 T4 순간 백로그의 산포다.
treatment run4(N=8)와 run8(N=825)의 100배 차이는 방어의 차이가 아니라 그 순간 lag 의 차이다.

### 6.3 처리량 차이

treatment 가 주문을 더 많이 만들었다(CONFIRMED med 72,871.5 vs 68,060, +7.1%, U=23 — 임계값과 동일한 경계).
투입 부하(계획 도착·rate·duration·pool·drop·cart_add_fail)는 arm 간 유의차가 없으므로 이는 **산출** 차이다.
방향은 보수적(더 많은 성공 주문 = 더 많은 위반 기회)이지만, 원시 N′·money_leak 의 분모가 arm 간 다르다는 뜻이므로
§2.3 의 정규화 지표를 함께 봐야 한다. **"완전히 동일한 조건의 비교"라고는 말할 수 없다.**

### 6.4 T2/T4 분리의 근사성

- 두 폴트는 DB 지문이 같고, 귀속은 오직 `chaos.log` 주입시각과 PENDING 생성 분(minute) 클러스터의 **시각 상관**이다.
- 창 `[M−2, M+1]` 은 임의 선택이다. 경계 민감 사례 2건과 중첩 사례 1건이 있다(§4.7).
- 주입 시각은 폴트 **시작** 시각이고 T4 는 재생성 완료가 25~91초 뒤라(T2-run1: 07:44:41 → 07:46:12) 실제 손상 창이 +1분 상한보다 길다.
- T4 몫은 T1 재기동 여파를 흡수할 수 있는 **상한**이다(§4.7).
- **control 에는 교차검증 수단이 없다** — `a_T2T4` 가 10/10 런 n/a 이므로 마커 쿼리로 확인할 수 없고 타임스탬프 상관에만 의존한다.
  treatment 에 있는 검산(`a_T2T4 − v3a` 가 9/10 런에서 0 초과, 차이 0~5, T2-run10 만 동일)이 control 에는 없다.
- 해소 방법: `FAULTS=T2,T3,T1`(T4 제외) 및 `FAULTS=T4` 단독, `FAULTS=T2` 단독 절제 런. **이 리포트에는 절제 런이 없다.**
  T2/T4 수치를 확정값으로 인용하면 안 된다.

### 6.5 정착(quiescence) — 20/20 도달 확인됨, 다만 `results/` 밖 로그에 근거한다

`verify-consistency.sh` 스스로 "정착 이후 값이라야 유효하다 — 부하 중이면 in-flight 가 그대로 양수로 잡힌다"고
경고한다. treatment 의 양수 `o_L1`(43/325/394/490)과 `v3a` 전량이 정확히 게이트 실패 시 오염되는 값이므로
정착 도달은 이 리포트 전체의 전제다.

**절차상 구멍이 있었다**: 측정 당시 `quiescence-gate.sh` 는 결과를 stdout 에만 찍고 `results/` 에 남기지 않았고
(tee 없음), TIMEOUT 600s 시 `exit 2` 로 끝나는데 README 실행 절차 7단계는 다음 줄에서 `&&` 없이 verify 를
무조건 실행한다 — **게이트가 TIMEOUT 나도 verify.txt 는 똑같이 생성된다.** 즉 `results/` 3종
(verify/chaos/k6)만으로는 정착 여부를 알 수 없다.

**다만 이번 20런은 배치 실행 로그에 게이트 출력이 남아 사후 검증됐다.** 20/20 런 전부:

```text
[quiescence] 정착 완료 ✓ — 3회 연속 변화 없음 (outbox o=0 u=0, pending/paid=<N>, lag=0)
```

게이트 4조건이 모두 충족됐다 — outbox 미발행 0(양 DB) · **kafka consumer lag = 0** · PENDING 3회 연속 불변.
앞서 "미확인"으로 남겨둔 lag 과 PENDING 불변이 여기서 해소된다.

추가 방증: 게이트가 마지막으로 관측한 `pending/paid` 값이 **20/20 런에서 verify 의 `v3a` 와 정확히 일치**한다
(T2-run1 319, T2-run4 8, T2-run8 825, C2-run1 778, C2-run2 1,222, C2-run10 230 …).
게이트 통과 시점과 verify 실행 시점 사이에 상태 변화가 없었다는 뜻이다.

> **수정됨** (커밋 `386f337`, 양 arm 체리픽): `RUN_LABEL` 이 설정돼 있으면 게이트가 출력을
> `results/$LABEL-quiescence.log` 로 tee 한다. 다음 런부터는 측정 산출물이 4종이 되어
> `results/` 만으로 정착 여부를 재검할 수 있다.
> 남은 과제: README 절차에서 게이트 exit code 를 verify 실행 조건으로 거는 것(`&&`)은 아직 반영하지 않았다 —
> 게이트가 실패한 런을 자동으로 배제할지, 값을 남기고 사후 판단할지는 측정 정책의 문제라 별도로 정할 사안이다.

### 6.6 KPI 정의 자체의 한계

- `N` 은 건(주문) · 개(상품 수량) · 행(레코드)을 합산하는 **무차원 합**이다. 물리적 의미가 있는 양이 아니다.
- 원 산식은 v2b + v2c 를 이중 계상한다(§2.1). 이 리포트는 `N′ = N − v2c` 를 쓴다.
- `money_leak` 은 독립 축이 아니라 ⑤ 의 화폐 표현이다(§2.4). "362.9배"를 인용할 때는
  **이 배율의 98%가 중복 결제 건수 차에서 온다**는 점을 함께 적어야 한다.
- `d5`(processed_events 총 행수)로는 중복 배달 '횟수'를 계수할 수 없고 control 은 테이블 자체가 없다.
  **"이벤트가 몇 번 재배달됐는가"는 양 arm 어느 쪽에서도 측정되지 않았다.**

### 6.7 control 실측치는 ①②에서 하한

- ①: k6 재전송 overlay 가 카트 소비 경합에 걸려 주입 1,388~1,550건 중 4~9%만 관측 가능했다(§4.1).
  추가로 '생성 − 의도 차분'이 20/20 런 0 으로 클램프됐다.
- ②: hot 아이템 재고가 20/20 런 전부 1000 → 0 완전 소진(포화)이라 v2b = v2c 로 수렴한 상태에서 측정됐다.

### 6.8 개별 귀속의 한계 — 방어 5종 동시 토글

이 실험은 방어 5종을 **하나씩이 아니라 동시에** 껐다 켰다. 따라서 "①의 감소분은 방어 ① 덕"이라는 서술은
지표별로는 그럴듯해도 **인과적으로 분리되지 않았다.** 실제로 §4.7 에서 보듯 ⑤ dedup 제거가 내부 이벤트량을 1.8배로 늘려
③④⑤ 와 T2 몫에까지 교란을 일으킨다. 단일변수 귀속이 필요하면 방어별 pre/post 런이 따로 필요하다.

동시에, **개입 범위가 main 소스 6개 파일에 국한되고 설정·에러핸들러·인프라·QA 하네스는 완전히 동일**하다는 점은
(§1.1·§1.2) 이 실험의 타당성을 지지한다 — 관측된 차이가 '방어 5종 이외의 무언가' 때문일 여지는 좁다.

### 6.9 일반화 불가

- 단일 환경 · 단일 하드웨어 · 단일 부하 프로파일(rate 90, duration 1,112s, rich_pool 300, hot id=10001 init=1000)의 20런이다.
  다른 도착률 · 다른 재고 분포 · 다른 인프라에서 같은 배율이 재현된다는 근거는 이 표본에 없다.
  특히 hot 아이템 1개에 경합이 집중된 설계라 ②·④ 의 크기는 이 시나리오 고유값이다.
- **ORDER_TARGET 미달의 원인 정정**: k6 는 constant-arrival-rate 이고 `duration = 100000/90 = 1,111s`(실측 1,112s)이므로
  도착 수 상한은 설계상 100,080이다. 계획 도착은 **20/20 런 전부 100% 집행**됐다(iterations + dropped = 100,080~100,081).
  주문 시도가 79,771~86,717 로 줄어든 것은 `cart_add_fail`(12.9~19.9%) 때문이며,
  k6 스크립트는 이를 "hot SKU 소진 후 NOT_ENOUGH_ITEM_COUNT — 정상 backpressure"로 명시한다.
  '부하가 중간에 끊겨 목표에 못 미쳤다'가 아니다. 다만 결과가 **실측 6.1~7.6만 건 규모의 관측**이라는 점,
  10만 건까지 밀었을 때 잔여가 선형으로 늘어난다는 근거가 없다는 점은 그대로다.
- 각 arm 의 run1(T2-run1, C2-run1)이 동시에 그 arm 의 2xx율 최저(75.52% / 77.42%) · http_req_failed 최고를 기록했다.
  **원인은 미상이다** — 매 런 `down -v` 로 볼륨을 지우고 다시 띄우므로 MySQL 버퍼풀도 JVM JIT 도 20런 전부 콜드에서 시작하며,
  '첫 런 워밍업' 가설로는 설명되지 않는다(T2-run2 앞에는 1.5시간 공백이 있는데 정상치다). 호스트 상태 차이 가능성.
  두 런을 배제할 근거는 없으므로 range 는 그대로 보고하되 **'정상 운영 범위'로 읽으면 안 된다.**
- latency 는 양 arm 모두 p(99) ≈ 10,000ms 로 클라이언트 타임아웃 상한에 포화돼 있어 arm 비교 지표로 쓸 수 없다.
  **이 실험은 성능이 아니라 정합성에 대해서만 발언한다.**
- `outbox_events` / `processed_events` 는 런 스코프 컬럼이 없는 전역 누적 계수다. `s_oc` 와 생성 수의 일치로
  오염이 없다고 판단했지만 이는 **간접 증거**이며, 런별 격리를 보장하는 스키마 수준의 장치는 없다.

## 7. 결론 요약

1. **방어 5종이 직접 겨냥한 위반 ①②④⑤ 는 treatment 10/10 런에서 전부 0, control 10/10 런에서 전부 > 0 이다.**
   v1(①) 90 → 0, v2c(②) 109.5 → 0, d4b(④) 377 → 0, o_L1(⑤) 부호 음수 10/10 → 음수 런 0건. 네 지표 모두 범위가 겹치지 않는다.
2. **집계 KPI: N′ 722.5 → 200 (3.61배).** 단 범위는 겹치며(treatment 최악 825 > control 최선 418),
   단일 런의 N′ 로 arm 을 판별할 수는 없다.
3. **treatment 의 잔여는 '위반'이 아니라 '배달 유실'이다.** N = v3a 가 10/10 런 일치 —
   ①②④⑤ 기여분은 0 이고 전량 PENDING/PAID 방치다. 그중 99.7%가 T4(kafka 로그·오프셋 전소) 창에 몰린다.
4. **money_leak 152,231,000 → 419,500(362.9배)은 독립 축이 아니다** — 98%가 ⑤ 중복 결제의 화폐 표현이다(§2.4).
5. **T4 계열 잔여는 arm 간 유의차가 없다**(U=38). 현재 outbox 는 `sent_at` 을 찍은 뒤 하류 마커를 확인하지 않아
   브로커가 로그를 잃으면 복구 경로가 없다. 이것이 treatment 잔여의 실질적 전부다.
   다만 T2/T4 분리는 시각 상관 추정이므로(§6.4), **"T4 대책이 필요하다"는 권고도 절제 런 이후에 확정해야 한다.**
